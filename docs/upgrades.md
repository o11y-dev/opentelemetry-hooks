# Upgrade and rollback

Managed fleets use the [Jamf/Intune procedures](managed-deployment.md#rotation-and-lifecycle).
Stage an approved hash-locked bundle, verify registration and backend delivery,
then expand the pilot. The deployment scripts retain the previous complete runtime
for rollback; restore matching managed policy separately. Uninstall unregisters
owned hooks before removing the launcher and retains credentials, runtime versions,
per-user queues and quarantine for explicit administrator cleanup.

This capture pipeline changes defaults and consumer contracts. Before upgrading:

1. Record the package version and installer, and back up `otel_config.json`,
   managed policy and hook registrations. Review the [changelog](../CHANGELOG.md).
2. Replace retired content flags with an explicit `capture.mode` and path policy.
   Omitting the mode selects `metadata_only`; hook logs default off. Use
   `logs.enabled` to enable the log signal. Existing runtime aliases remain
   supported; old per-content and per-event log switches do not restore capture.
3. Update consumers that rely on separate shell/MCP/tool/conversation logs or old
   flattened fields. Validate their interpretation against the
   [telemetry contract](telemetry-reference.md), not just successful export.
4. Install the approved version, rerun setup and verify real sessions in the pilot.

For rollback, stop active pilot sessions, reinstall the previously tested version
with the package manager that owns `otel-hook`, restore its configuration and
managed policy, then rerun setup in the original scope and verify delivery.
If Reflect owns the hook environment, roll back through Reflect's package manager;
do not install a competing standalone copy. Unregister hooks to pause collection
if needed; use `--no-global --cwd /path/to/repo` for project registrations.

Rollback does not retract exported data. New capture policies isolate pending
state, and older versions may not understand it. Preserve state for investigation
and verify which batches replay before resuming collection. See
[configuration and state behavior](configuration.md).


## Schema version 2 rollout

Review the [schema-v2 contract](telemetry-reference.md#schema-version-2) and
[validation record](telemetry-v2-validation.md). Rebuild consumers that used
capture mappings to redefine identity/status/usage: those targets now fail closed.
Use a consumer-side derived field or an unprotected custom mapping instead.
Callback IDs generated by hooks identify individual observations; replay reuses
them, while separate identical callbacks get different IDs. Inclusive token
accounting and omitted lifecycle operation names can change existing queries.

Start a canary with metadata-only capture and logs off. Verify parent IDs,
callback times, collector reject metrics, queue/quarantine growth and hook latency
on the target OS and harness. Enable selected content and bounded logs only under
the approved capture policy. Rerun setup after upgrading callback registrations.
Compare a full session and concurrent subagent session before expanding rollout.
No live vendor canary or production rollout is implied by fixture replay.

The [Coralogix/OTel audit](coralogix-compatibility.md) records current naming and
remaining conformance checks. Cache writes now also emit
`gen_ai.usage.cache_write.input_tokens`; `cache_creation.input_tokens` retains
the same value. Tool names now also emit `gen_ai.tool.name`. Existing hook span
names and legacy fields remain; do not sum aliases or interpret `gen_ai.system`
as the provider. `gen_ai.request.top_k` is now emitted as an integer.

For rollback, stop the canary, preserve policy-specific queues/quarantine for
investigation, restore the prior package and configuration, rerun setup, and
verify delivery. Do not copy schema-v2 records into an older policy queue or
assume rollback deletes previously exported data.
